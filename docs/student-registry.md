# Central student registry

Student Management is available at `/headteacher/students`. Every active Head Teacher can manage the school registry. This installation represents one school; departments are not separate schools or authorization tenants. Teachers continue to see and manage only their own classes through the existing teacher APIs.

## Deployment

Apply all existing migrations in order, including `018_teacher_group_invitations.sql`, then apply the complete `backend/supabase/migrations/019_student_registry.sql` in the existing Supabase project. Deploy the backend and frontend together. The migration adds tables, account-provider fields, functions, synchronization triggers and RLS policies. It preserves existing accounts, passwords, imported students and class memberships, and backfills them into the central directory. No live database migration is performed by the application build or tests.

Set `STUDENT_REGISTRY_SECRET` to a stable random value of at least 32 characters. `JWT_SECRET` is a compatibility fallback. Keep the secret stable to preserve copied links and registration codes. Configure `FRONTEND_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and preferably `SUPABASE_PUBLISHABLE_KEY` on the backend. The service-role key is never needed in the Vue environment. Configure the existing `MAIL_API_URL` and `MAIL_API_KEY` so students can receive verification codes. Production uses the existing Redis-backed request limits.

New registry students use Supabase Auth's email/password provider. Existing accounts keep their current authentication provider and password hashes. The backend verifies a new student's credentials using a fresh, nonpersistent Supabase client, verifies the returned identity against the account's Auth ID, then issues the existing EduMatch application session. CAPTCHA, lockouts, login email OTP settings, role checks, session revocation and navigation remain in place. Password change and reset update the linked Supabase Auth account; they never introduce a second bcrypt password. See Supabase's [server-side account creation](https://supabase.com/docs/reference/javascript/auth-admin-createuser) and [password authentication](https://supabase.com/docs/reference/javascript/auth-signinwithpassword) APIs.

## School workflow

1. Download the Excel template. Upload one `.xlsx` workbook with only **First Name** and **Last Name** columns, up to 1,000 students and 2 MB. The server checks archive expansion limits, plain-text cells, missing names and duplicate identities. Preview and import both revalidate; a forged or stale preview cannot bypass database constraints.
2. Review invalid rows and possible duplicates. Full names are unique across the school using the existing Unicode normalization and case-insensitive name rules. Spacing, punctuation and accent similarities receive additional review warnings. The UI imports the valid rows selected by its preview and requires acknowledgement of possible duplicates. Identical names require school review rather than creating a second account or silently merging students.
3. Copy the shared school registration link and distribute each student's individual code privately. Export Excel includes the codes for unused registrations, their expiry, and the shared link, so the school can distribute them without creating individual accounts. Export respects the displayed search and filters. Existing pending rosters have no central code until **Issue Code** is used; their original class invitation remains supported.
4. Select pending or registered students and assign their teacher classes. Saving replaces the selected students' class assignments; clearing or replacing multiple assignments requires confirmation in the UI. One student can belong to multiple classes. Teachers are derived from the selected classes, never supplied by a student.
5. Students open `/auth/student-register/:token`, enter their individual code and matching full name, verify their own email, choose an available username and create a password. Registration creates one active Student account and approves every assigned class membership. Unassigned students can register and be assigned later.

Counts show all school records, registered students, pending registrations (including revoked/expired codes) and unassigned students. Search includes student names, usernames, emails and assigned teachers/classes. A shared link lasts 30 days and is reused until it expires or a Head Teacher replaces it. Individual codes last 30 days, are single-use, and can be revoked or renewed before registration. Renewal invalidates the old code. Active account-creation claims briefly block code/link changes so a registration already in progress can finish.

## Validation and recovery

The backend derives 128-bit registration codes and 256-bit link tokens using HMAC and random nonces. The database stores hashes for lookup; only authorized Head Teacher endpoints reconstruct unused codes for distribution. Possessing the shared link alone reveals no student directory or registration codes. Code and full-name verification returns a random, short-lived ticket, held only in page memory. The ticket, link version and code version must still match when each critical operation commits.

Email verification uses a six-digit code, ten-minute expiry, a 60-second resend cooldown and five persisted attempts per challenge. Successful verification returns a separate fifteen-minute proof bound to the verified email and registration session. Student names, roles, school scope and class assignments come from trusted database records. Usernames use the existing 3–30 character alphabet and case-insensitive unique database index; suggestions are checked for availability, and the final database transaction remains authoritative.

Supabase Auth creation and Postgres enrollment are separate operations. A short-lived, serialized claim reserves the student and username before the Auth call. Only an email verified by this flow is confirmed through the server-only Auth Admin API. Finalization checks the Auth user's confirmed email and trusted `app_metadata` against the registration claim, then atomically creates the public account, consumes the code and enrolls its classes. Repeated submission recovers the same claim. A fresh code/name session and fresh email verification can resume this registry's own unfinished Auth identity using its retained claim ledger; unrelated Auth accounts are never adopted by email alone. Failed database responses never trigger deletion of an account that might already have committed.

The verified sign-in email of a new Supabase Auth student is readonly in profile editing to prevent the public account and Auth identity from diverging. Email identity changes require an administrator-managed verified change. Existing students retain their previous profile and sign-in behavior.

## Data access

`student_registry` holds one school identity; `student_registry_assignments` holds pending and registered class membership; `student_registry_links` holds the current shared link; `student_registry_sessions` holds private challenges and active leases; `student_registry_claims` retains the private ownership ledger for safe recovery. Approved membership remains in the existing `subject_enrollments` table, which feeds the Teacher Class List. Triggers synchronize legacy account creation, old class rosters, teacher enrollment approvals and class removals with the registry.

All management writes use service-role-only functions that recheck the caller's active Head Teacher role in the database. Public registration functions are callable only by the trusted backend. Anonymous users cannot query the registry, codes or verification state. Authenticated Supabase users receive column-limited directory reads through RLS: active Head Teachers can read the directory, teachers can read only students assigned to their classes, and students can read their own directory record. These policies map `auth.uid()` through the trusted `users.auth_user_id`; they do not trust browser-supplied role metadata. Existing local accounts use the backend's role checks; optional administrator-managed Auth identity mapping can enable direct RLS reads without changing their password provider.

Sensitive API responses are not cached. Token paths and registration proofs/codes are redacted from request/audit logging. Expired session records with a claim are retained for safe recovery of unfinished Auth creation. Do not delete claim ledgers while investigating incomplete registrations. The application-data reset script lists the new registry tables; it does not delete Supabase Auth identities or Storage objects.

## Verification

Run `npm test` in `backend` and `npm run build` in `frontend`. Registry database tests execute the production SQL in disposable PGlite PostgreSQL with a test-only Auth schema. Service and credential tests mock Supabase Auth and email delivery. They cover missing/duplicate names, authoritative role checks, token/code expiry and replay, email verification attempts, case-insensitive usernames, multiple class assignments, legacy backfill, RLS restrictions, partial account creation and retry, and coexistence with existing sign-in. These checks do not alter the school database or send real email.

Run `node frontend/scripts/check-student-registry.cjs` and `node frontend/scripts/check-student-registration.cjs` from the repository root for compiled Vue workflow checks with mocked APIs. These checks make no HTTP requests.
