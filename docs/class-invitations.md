# Student roster invitations

The active server uses Supabase Postgres persistence. After migrations 001–013, apply these migrations in order through the Supabase SQL editor or your normal migration process:

1. `backend/supabase/migrations/014_create_class_invitations.sql`
2. `backend/supabase/migrations/015_name_based_class_registration.sql`
3. `backend/supabase/migrations/016_advisory_class_invitations.sql`

Installations already running migration 014 still need 015 and 016; installations running 015 need 016. Deploy backend/frontend together after the upgrade. Migration 015 preserves existing invitation links, roster rows and registered status while removing legacy registration-code hashes and replacing the registration RPC. Migration 016 adds the advisory-section marker on classes and restricts invitations to the teacher's designated advisory class and section. It preserves existing registered accounts and memberships; invitations for a different class or section cannot be used with the current advisory assignment. The migrations use transactions and enable RLS; only the backend service role can execute import/registration RPCs or read invitation rosters. Never expose the service-role key in frontend configuration.

Existing student accounts with the same full name after case, whitespace and Unicode normalization must be reviewed by an administrator before the migration's student identity index can be installed. The workflow refuses ambiguous names. It does not merge or delete existing accounts.

Set `CLASS_INVITATION_SECRET` to a stable random secret of at least 32 characters, and set `FRONTEND_URL` to the public Vue app origin. Existing `JWT_SECRET` is used as a fallback. Keep the invitation secret stable across restarts and deployments: rotating it invalidates teacher-reconstructed class links. Use a dedicated secret so normal JWT rotation does not affect invitations. Class-link tokens are HMAC-derived and stored only as SHA-256 hashes. There are no per-student registration codes or code exports.

Teachers upload an `.xlsx` workbook, up to 2 MB and 1000 students, with one student worksheet containing only `First Name` and `Last Name` headers in row 1. Excel tables are supported. Separate `Instructions`, notes, blank and formatted blank tabs can remain in the workbook; the backend selects the worksheet by its name-column headers, regardless of tab order. If multiple worksheets contain both required headers, upload each student list separately. Both name parts must be plain text. Extra columns on the selected student worksheet, including `Section`, are rejected. The modal loads the teacher's designated advisory class and active advisory section automatically with `GET /api/teacher/class-invitations/advisory`; teachers do not select a class or section. The backend ensures the default advisory class exists and reads the current assignment again before preview, creation and renewal. Teachers without an active advisory section must ask their Head Teacher or school administrator to update the assignment. The backend composes each full name from the two name parts and ignores row-level full names, sections and section IDs supplied by clients.

Invalid names, missing name parts, formulas, repeated composed names and names already imported or registered are rejected during preview and again at import. Teachers can explicitly exclude invalid rows, or correct the spreadsheet and upload it again. The server validates every submitted row and reads the active section again even when the client has already previewed it. Preview requests use only the multipart field `file`; creation uses `{ "records": [{ "firstName": "Juan", "lastName": "dela Cruz" }], "expiresInDays": 30 }`. Preview rejects extra multipart fields. Creation rejects top-level `subjectId`, `classId`, `sectionId`, `advisorySectionId` and `teacherId` fields because the authenticated teacher's advisory assignment supplies those values.

Each advisory class has one shareable invitation link. A new import appends new names to its existing roster and renews the invitation expiry to at least the requested date (1–90 days, default 30). Teachers can also renew an existing invitation without reimporting its roster with `POST /api/teacher/class-invitations/:id/renew` and `{ "expiresInDays": 30 }`. Renewal requires the invitation and its roster to match the teacher's current advisory class and section. Renewing lets unregistered students open the link again; students who have already registered remain blocked from registering a second time. Expired links display an expiry error; the teacher sees expiry and registration counts.

Students open the class link and enter their imported full name. Matching is exact after case, whitespace and Unicode normalization; spelling errors, partial names, and names from another class invitation are rejected. `POST /api/auth/class-invitations/:token/verify` accepts `{ "fullName": "Juan dela Cruz" }` and returns only the matching student's name and section. Registration accepts `{ "fullName": "Juan dela Cruz", "email": "juan@gmail.com", "username": "juan.cruz", "password": "StrongPass1", "confirmPassword": "StrongPass1" }`. The public API never lists the roster. Full-name matching checks whether a name is on the imported list; it does not prove that the person entering the name is that student.

New students use a Gmail address, a 3–30 character username (letter/number first; letters, numbers, dots, underscores, hyphens thereafter), and the existing password policy (8–16 characters, uppercase/lowercase/number). Username suggestions are checked case-insensitively; unique database indexes remain authoritative at commit. Account creation, advisory-class approval, section assignment, and marking the roster entry registered commit together. Failed or concurrent requests cannot partly register a student or create a second account. Successful registration sends students to the normal sign-in flow.

Public invitation reads, username checks, and verification/registration have separate rate limits. Configure the existing `REDIS_URL` for shared limits when deploying multiple backend instances. The Teacher Student Management page refreshes counts/status while open; successful registrations are approved automatically rather than added to the manual enrollment approval queue. Existing individual-account creation and class-code enrollment remain available.

## Troubleshooting

Run `node scripts/check-class-invitations.js` from `backend` to check the required columns and signing-secret configuration against the configured Supabase project. This read-only check returns no student records or credential values. It does not verify RPC definitions, so apply each complete migration rather than adding only the missing column. Missing schema now returns the actionable message "Student invitations need a database update. Ask your administrator to complete the invitation database setup."

If invitations show “Student invitations are temporarily unavailable. Please try again later.”, first confirm that migrations 014, 015 and 016 were applied to the same Supabase project configured by the backend. The message sanitizes unexpected persistence errors and can also represent a connection or access problem. In particular, existing invitation tables do not prove the schema is current: migration 016 must add `public.subjects.advisory_section_id` and update the invitation RPCs. A missing advisory-section column or a schema-cache error for that column means the advisory upgrade is incomplete or the cache needs refreshing after the migration. Apply the missing migration through the normal deployment process, confirm the column is available to the backend, and retry the advisory request. A teacher with no active advisory section needs an administrator to update their assignment.

## Verification

Run `npm test` from `backend` for the existing regression suite and the invitation tests. `classInvitationService.test.js` reads real Excel workbooks and tests server validation. `classInvitationDatabase.test.js` executes the actual migrations and import/registration/renewal RPCs in disposable in-memory PostgreSQL with PGlite. It checks correct membership, duplicate prevention, single registration per imported name, renewal, permissions, upgrade preservation, and rollback after an enrollment write failure. These tests do not modify the school database.

Run `npm run build` from `frontend`. With the local frontend running, execute `node scripts/check-class-invitation-registration.cjs` and `node scripts/check-class-invitation-teacher.cjs` from `frontend` for mocked browser workflow and mobile checks. Override `INVITATION_UI_URL` if the server is not at `http://127.0.0.1:5173`. Browser checks validate the UI; database tests validate transaction behavior. A final deployment smoke test requires migrations through 016 and the invitation secret in the target environment.
