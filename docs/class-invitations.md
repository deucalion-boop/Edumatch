# Student roster invitations

The active server uses Supabase Postgres persistence. Apply `backend/supabase/migrations/014_create_class_invitations.sql` after migrations 001–013, then apply `backend/supabase/migrations/015_name_based_class_registration.sql` through the Supabase SQL editor or your normal migration process. Installations already running migration 014 apply only 015. Deploy backend/frontend together after the upgrade. Migration 015 preserves existing invitation links, roster rows and registered status while removing legacy registration-code hashes and replacing the registration RPC. The migrations use transactions and enable RLS; only the backend service role can execute import/registration RPCs or read invitation rosters. Never expose the service-role key in frontend configuration.

Existing student accounts with the same full name after case, whitespace and Unicode normalization must be reviewed by an administrator before the migration's student identity index can be installed. The workflow refuses ambiguous names. It does not merge or delete existing accounts.

Set `CLASS_INVITATION_SECRET` to a stable random secret of at least 32 characters, and set `FRONTEND_URL` to the public Vue app origin. Existing `JWT_SECRET` is used as a fallback. Keep the invitation secret stable across restarts and deployments: rotating it invalidates teacher-reconstructed class links. Use a dedicated secret so normal JWT rotation does not affect invitations. Class-link tokens are HMAC-derived and stored only as SHA-256 hashes. There are no per-student registration codes or code exports.

Teachers upload an `.xlsx` workbook, up to 2 MB and 1000 students, with one student worksheet containing only `First Name` and `Last Name` headers in row 1. Excel tables are supported. Separate `Instructions`, notes, blank and formatted blank tabs can remain in the workbook; the backend selects the worksheet by its name-column headers, regardless of tab order. If multiple worksheets contain both required headers, upload each student list separately. Both name parts must be plain text. Extra columns on the selected student worksheet, including `Section`, are rejected. Select the class and one active school section in the invitation modal before uploading; that section applies to every row in the import. When no section is supplied, the backend uses the teacher's current active advisory section read from the database. Teachers without an active advisory section must select one. The backend composes each full name from the two name parts and ignores row-level full names, sections and section IDs supplied by clients.

Invalid names, missing name parts, formulas, repeated composed names and names already imported or registered are rejected during preview and again at import. Teachers can explicitly exclude invalid rows, or correct the spreadsheet and upload it again. The server validates every submitted row and reads the active section again even when the client has already previewed it. Preview requests use multipart fields `file`, `subjectId` and optional `sectionId`; creation uses `{ "subjectId": "class-id", "sectionId": "section-id", "records": [{ "firstName": "Juan", "lastName": "dela Cruz" }], "expiresInDays": 30 }`.

Each class has one shareable invitation link. A new import appends new names to its existing roster and renews the invitation expiry to at least the requested date (1–90 days, default 30). Teachers can also renew an existing invitation without reimporting its roster with `POST /api/teacher/class-invitations/:id/renew` and `{ "expiresInDays": 30 }`. Renewing lets unregistered students open the link again; students who have already registered remain blocked from registering a second time. Expired links display an expiry error; the teacher sees expiry and registration counts.

Students open the class link and enter their imported full name. Matching is exact after case, whitespace and Unicode normalization; spelling errors, partial names, and names from another class invitation are rejected. `POST /api/auth/class-invitations/:token/verify` accepts `{ "fullName": "Juan dela Cruz" }` and returns only the matching student's name and section. Registration accepts `{ "fullName": "Juan dela Cruz", "email": "juan@gmail.com", "username": "juan.cruz", "password": "StrongPass1", "confirmPassword": "StrongPass1" }`. The public API never lists the roster. Full-name matching checks whether a name is on the imported list; it does not prove that the person entering the name is that student.

New students use a Gmail address, a 3–30 character username (letter/number first; letters, numbers, dots, underscores, hyphens thereafter), and the existing password policy (8–16 characters, uppercase/lowercase/number). Username suggestions are checked case-insensitively; unique database indexes remain authoritative at commit. Account creation, selected-class approval, section assignment, and marking the roster entry registered commit together. Failed or concurrent requests cannot partly register a student or create a second account. Successful registration sends students to the normal sign-in flow.

Public invitation reads, username checks, and verification/registration have separate rate limits. Configure the existing `REDIS_URL` for shared limits when deploying multiple backend instances. The Teacher Student Management page refreshes counts/status while open; successful registrations are approved automatically rather than added to the manual enrollment approval queue. Existing individual-account creation and class-code enrollment remain available.

## Verification

Run `npm test` from `backend` for the existing regression suite and the invitation tests. `classInvitationService.test.js` reads real Excel workbooks and tests server validation. `classInvitationDatabase.test.js` executes the actual migrations and import/registration/renewal RPCs in disposable in-memory PostgreSQL with PGlite. It checks correct membership, duplicate prevention, single registration per imported name, renewal, permissions, upgrade preservation, and rollback after an enrollment write failure. These tests do not modify the school database.

Run `npm run build` from `frontend`. With the local frontend running, execute `node scripts/check-class-invitation-registration.cjs` and `node scripts/check-class-invitation-teacher.cjs` from `frontend` for mocked browser workflow and mobile checks. Override `INVITATION_UI_URL` if the server is not at `http://127.0.0.1:5173`. Browser checks validate the UI; database tests validate transaction behavior. A final deployment smoke test requires the migration and invitation secret in the target environment.
