# Student roster invitations

The active server uses Supabase Postgres persistence. Apply `backend/supabase/migrations/014_create_class_invitations.sql` after migrations 001–013 through the Supabase SQL editor or your normal migration process, then deploy backend/frontend together. The migration is a transaction and enables RLS; only the backend service role can execute import/registration RPCs or read invitation rosters. Never expose the service-role key in frontend configuration.

Existing student accounts with the same full name after case, whitespace and Unicode normalization must be reviewed by an administrator before the migration's student identity index can be installed. The workflow refuses ambiguous names rather than assigning a code to the wrong student. It does not merge or delete existing accounts.

Set `CLASS_INVITATION_SECRET` to a stable random secret of at least 32 characters, and set `FRONTEND_URL` to the public Vue app origin. Existing `JWT_SECRET` is used as a fallback. Keep the invitation secret stable across restarts and deployments: rotating it invalidates teacher-reconstructed links and codes. Use a dedicated secret so normal JWT rotation does not affect invitations. Tokens and codes are HMAC-derived and stored only as SHA-256 hashes; downloadable spreadsheets contain sensitive codes and should be shared privately with the intended students.

Teachers upload one non-empty `.xlsx` worksheet, up to 2 MB and 1000 students, with only `First Name` and `Last Name` headers in row 1. Both name parts must be plain text. Extra columns, including `Section`, are rejected. Select the class and one active school section in the invitation modal before uploading; that section applies to every row in the import. When no section is supplied, the backend uses the teacher's current active advisory section read from the database. Teachers without an active advisory section must select one. The backend composes each full name from the two name parts and ignores row-level full names, sections and section IDs supplied by clients.

Invalid names, missing name parts, formulas, repeated composed names and names already imported or registered are rejected during preview and again at import. Teachers can explicitly exclude invalid rows, or correct the spreadsheet and upload it again. The server validates every submitted row and reads the active section again even when the client has already previewed it. Preview requests use multipart fields `file`, `subjectId` and optional `sectionId`; creation uses `{ "subjectId": "class-id", "sectionId": "section-id", "records": [{ "firstName": "Juan", "lastName": "dela Cruz" }], "expiresInDays": 30 }`.

Each class has one shareable invitation link. A new import appends new names to its existing roster and renews the invitation expiry to at least the requested date (1–90 days, default 30). Teachers can also renew an existing invitation without reimporting its roster with `POST /api/teacher/class-invitations/:id/renew` and `{ "expiresInDays": 30 }`. Renewing makes the class's previously unregistered codes usable until that date. Registered codes stay consumed. Expired links display an expiry error; the teacher sees expiry and registration counts. Students must provide their own code and matching full name; the public API never lists other students.

New students use a Gmail address, a 3–30 character username (letter/number first; letters, numbers, dots, underscores, hyphens thereafter), and the existing password policy (8–16 characters, uppercase/lowercase/number). Username suggestions are checked case-insensitively; unique database indexes remain authoritative at commit. Account creation, selected-class approval, section assignment, and code consumption commit together. Failed or concurrent requests cannot partly consume a code or create a second account. Successful registration sends students to the normal sign-in flow.

Public invitation reads, username checks, and verification/registration have separate rate limits. Configure the existing `REDIS_URL` for shared limits when deploying multiple backend instances. The Teacher Student Management page refreshes counts/status while open; successful registrations are approved automatically rather than added to the manual enrollment approval queue. Existing individual-account creation and class-code enrollment remain available.

## Verification

Run `npm test` from `backend` for the existing regression suite and the invitation tests. `classInvitationService.test.js` reads real Excel workbooks and tests server validation. `classInvitationDatabase.test.js` executes the actual migrations and import/registration/renewal RPCs in disposable in-memory PostgreSQL with PGlite. It checks correct membership, duplicate prevention, code consumption, renewal, permissions, and rollback after an enrollment write failure. These tests do not modify the school database.

Run `npm run build` from `frontend`. With the local frontend running, execute `node scripts/check-class-invitation-registration.cjs` and `node scripts/check-class-invitation-teacher.cjs` from `frontend` for mocked browser workflow and mobile checks. Override `INVITATION_UI_URL` if the server is not at `http://127.0.0.1:5173`. Browser checks validate the UI; database tests validate transaction behavior. A final deployment smoke test requires the migration and invitation secret in the target environment.
