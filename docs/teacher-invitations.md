# Teacher invitations

Teacher Management uses one shared department registration link. A Head Teacher selects **Generate Group Link**, copies the link into the teachers’ group chat, and lets each teacher enter their own details and verify their email. There are no teacher-name or email fields to fill in and no individual invitation emails in this workflow. The link supports multiple registrations until it expires or is revoked.

Choose a 12-, 24-, or 48-hour lifetime; the default is 48 hours. The backend accepts integer lifetimes from 1 to 48 hours. Generate returns the existing active link unchanged, so repeated clicks do not create competing links. **Renew Link** rotates the URL and sets a fresh expiry; the previous URL and unfinished verification sessions stop working. **Revoke Link** stops new registrations. Existing teacher accounts remain active. The table displays Active, Expired or Revoked and the number of registrations. The directory refreshes when that count increases.

## Deployment

Teacher registration uses the application’s existing Supabase Postgres account persistence and sign-in flow. After the existing migrations through 016, apply `backend/supabase/migrations/017_teacher_invitations.sql` and then `backend/supabase/migrations/018_teacher_group_invitations.sql` to the same Supabase project as the backend. Deploy backend and frontend together. Installations already running 017 still need 018 for group links. Run each complete migration, rather than creating only its tables. The upgrade preserves existing accounts and individual invitations; it adds private per-email registration state for shared links. Browser roles cannot read these tables or execute their functions.

Set `TEACHER_INVITATION_SECRET` to a stable random secret of at least 32 characters and configure `FRONTEND_URL` with the public Vue app URL. `CLASS_INVITATION_SECRET` and then `JWT_SECRET` are compatibility fallbacks. Keep the dedicated invitation secret stable across restarts and deployments. Links use HMAC with an invitation identifier and random nonce; only SHA-256 hashes are used for lookup. Renewal rotates the nonce and hash. Secrets, email codes, password hashes and verification proofs are never returned in management metadata. The backend service-role key stays on the server.

The existing mail API (`MAIL_API_URL` and `MAIL_API_KEY`) sends each teacher’s email verification code. Generating or renewing a group link does not send an invitation email. Failed code delivery invalidates that code and reports when another can be requested. Code requests and link renewal enforce a 60-second cooldown, with additional public request limits. Configure `REDIS_URL` for shared request limits across backend instances.

## Registration and access

The public route is `/auth/teacher-register/:token`. Its API validates the link before exposing its department or checking a username. Each teacher enters a full name, school or Gmail email, username and password, then verifies an emailed six-digit code. Codes expire in 10 minutes or when the link expires, whichever comes first. Five incorrect attempts lock that email’s challenge. A successful check returns a separate 15-minute verification proof held in the registration page’s memory. Verification state is separate for each teacher email, so several teachers can register through the same group link. Requesting a new code invalidates that email’s previous code and proof.

Username checks are debounced and case-insensitive, treat underscores literally, and return only suggestions checked for availability. Usernames use 3–30 letters, numbers, dots, underscores or hyphens, starting with a letter or number. The database's case-insensitive unique indexes remain authoritative when registration commits. Names support Unicode letters, spaces, apostrophes and hyphens up to 100 characters. Passwords follow the existing 8–16 character uppercase/lowercase/number policy and are hashed with bcrypt cost 12.

Registration checks the current group link, expiry, per-email verification proof, and the issuer’s active Head Teacher role and department again. Account creation, consuming that email’s proof and updating the registration count commit together. Concurrent or repeated requests cannot register the same email twice. The group link stays available for other teachers. The new account is active with the Teacher role, the issuing Head Teacher as `managed_by`, and that Head Teacher’s department and subject. It uses the existing sign-in flow. Head Teachers can subsequently assign an advisory section in Teacher Management.

EduMatch currently has one school per deployment, with departments managed by Head Teachers; it has no school/tenant table. Invitations preserve that existing school association and derive all permissions from the issuer. `SCHOOL_NAME`, if set, changes the public display name only and is not an authorization boundary. A future multi-school installation would need an explicit tenant model and corresponding access rules.

Teacher accounts accept valid school email addresses as well as Gmail throughout account persistence, sign-in and their profile. Teacher Management no longer exposes manual teacher creation controls or the teacher creation form. The legacy manual backend API remains for compatibility. Student creation and teacher administration remain available. Previous individual invitations appear as read-only history in the group-link panel; their single-use public registration and backend lifecycle remain supported. The application reset script `reset-keep-admin.sql` also removes invitation and group registration data; uploaded files are managed separately.

## API

Authenticated Head Teachers use `GET` and `POST /api/headteacher/teacher-invitations`, `POST /:id/resend`, and `POST /:id/revoke`. Group creation and renewal accept only the optional expiry setting: `{ "expiresInHours": 48 }`. New group creation rejects `name` and `email` fields. Each Head Teacher can see and manage only links they issued for their current department. Management rows identify shared links with `isGroup: true` and include `registrationCount`; backend `Pending` is displayed as Active for these rows. Role and department are never accepted from registration input.

Public APIs under `/api/auth/teacher-invitations/:token` are `GET /` for invitation details, `GET /username?username=...`, `POST /email-code` with `{email}`, `POST /verify-email` with `{email,code}`, and `POST /register` with `{fullName,email,username,password,confirmPassword,verificationToken}`. Sensitive responses use `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. Operational database errors are sanitized; a missing migration reports that teacher invitation setup needs a database update.

## Verification

Run `npm test` in `backend` and `npm run build` in `frontend`. Teacher invitation tests execute the real migrations/functions in disposable PGlite PostgreSQL and mock persistence/mail for service checks. They cover group reuse, several teacher registrations, per-email verification, ownership, expiry, revocation, rotation, attempts, replay and rollback, alongside legacy invitation compatibility. Email-policy/security tests cover school-email teacher accounts. These checks do not send real emails or modify the school database.
